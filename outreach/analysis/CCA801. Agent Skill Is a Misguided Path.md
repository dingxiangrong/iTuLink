
# CCA801. Agent-Skill Is a Misguided Path
## I. Prevailing Industry Misconception: Treating Scheduling Capabilities as Execution Skills

Across the entire Agent ecosystem, the common narrative is to equip AI with Skills, pile tools for Agents, and grant large-language models more capabilities.

The widespread industry belief: *Large-model + more Skills = a more powerful agent*.

This seemingly sound development pattern stems from misaligned architectural understanding. It is the root cause of today¡¯s Agent engineering chaos ¡ª poor governability, limited reusability, and lack of scalability.

**Core Thesis of this Document:**

There are no execution skills inherently belonging to AI or Agents. All so-called AI-Skills are container-based capabilities residing in external host systems. AI itself possesses zero execution capabilities; it only holds cognitive-scheduling capabilities.

## II. Setting the Record Straight: Large-Models Only Have Cognitive Capabilities, No Execution Capabilities

A large-model natively has four purely cognitive abilities: comprehension, reasoning, planning, and decision-making.

Actions commonly categorized as ¡°AI-skills¡± ¡ª reading-writing files, executing commands, operating computers, querying business data, submitting forms, invoking APIs ¡ª cannot be accomplished by the large-model alone. All of them rely on external host environments such as browsers, terminals, operating systems, backend services, and third-party systems.

A frequent industry counter-argument: Function-Calling is a native capability of large-models; selecting functions and filling parameters counts as an AI-skill.

This represents typical cognitive confusion:

> Deciding *what to invoke* and *how to invoke it* is cognitive scheduling, not business-level execution.

A project manager may coordinate construction workers and plan workflows, yet we would not claim ¡°the project manager possesses brick-laying and tiling construction skills¡±. **Cognitive scheduling ¡Ù real-world execution**. Confusing the two is the primary source of Agent-architecture disorder.

## III. Correct Paradigm: All Execution Capabilities Belong to CC Capability-Containers

The only valid architecture to resolve AI-Skill-driven chaos is the CC capability-container paradigm. Any host environment capable of completing `Input ¡ú Compute ¡ú Output` acts as an independent capability carrier. AI only mounts and schedules these carriers; it never owns execution capabilities.

Common standardized capability-containers:
- Front-end Browser = Web-CC (page navigation, form interaction, data query)
- Mobile App = Mobile-CC (voice, camera, native interaction)
- PC Operating-System = PC-CC (command-line, files, windows, device control)
- Back-end Business Service = Biz-CC (business CRUD, rule validation, workflow approval)
- MCP Server = Device-capability adaptation & transport container (unified communication layer)

All host-side capabilities register as standardized capability-anchors with unique identifiers, semantic descriptions, structured parameters, execution modes, and permission constraints.

> Sole responsibility of AI / Agent: Parse user intent ¡ú match scene focus ¡ú schedule corresponding container anchor ¡ú delegate execution to the host system.
> AI acts purely as a scheduling hub; it never generates capabilities.

## IV. Objective View of MCP: Historical Merit, Yet Not a Complete Architectural Solution

MCP is widely mythologized within the industry and treated as a full-fledged Agent architecture. This constitutes a severe layering misjudgment. We must objectively and dialectically define MCP¡¯s value and boundaries.

### 1. Real Historical Value of MCP (Not to Be Denied)

Released at the end of 2024, MCP emerged amid industry fragmentation. There existed no unified way for AI to connect external data, invoke tools, or interface with end-devices. Countless proprietary protocols proliferated with no universal standard.

MCP¡¯s key contribution lies in unifying communication protocols between AI and external systems. By analogy: USB standardized peripheral interfaces so mice, keyboards, USB-drives could interoperate. MCP solved the fundamental problem of *how AI talks to the outside world* and ended protocol fragmentation. This represents genuine historical merit.

### 2. Inherent Limitations of MCP: Merely a Transport Layer Without Architectural Governance

MCP belongs to the communication-protocol layer rather than the architectural-paradigm layer. The distinction is essential:

- **MCP**: Answers *how AI communicates with external systems, how tools transmit, and how results return*. It is a transport-standard for tool invocation.
- **CAP / CC Paradigm**: Answers *who owns capabilities, how to group them, how to converge per-scene, and how to govern at scale*. It represents a complete capability-organization architecture.

The critical shortcoming: MCP does not break free from traditional Skill-mindset. Its exposed tools list remains a one-dimensional flat collection described by verbose natural-language text and subject to probabilistic large-model interpretation. MCP merely wraps legacy Skill patterns inside a standardized protocol shell. It fails to resolve core Skill-pattern pain-points: lack of hierarchy, lack of scene awareness, poor testability, weak verifiability, and inability to scale.

### 3. Proper Layered-Relationship: CAP-Architecture Layer > MCP Transport-Layer

The two are not mutually-exclusive; they operate as complementary upper-lower layers.

MCP functions as a low-level transport adapter for CAP architecture. CAP can natively support MCP protocols and automatically convert MCP tools into standardized CC anchors.

## V. Practical Engineering Evidence: Skill-Pattern Has Hit Hard Limits (Nuwa-AI Case)

Our in-house project *Nuwa-AI* has demonstrated fatal inherent flaws of traditional Skill-patterns. These defects cannot be mitigated via prompt-tweaking or manual housekeeping; they originate from paradigm limitations.

### 1. Flat-list Structure: Growing Business Equals Growing Disorder

Skills are implemented as a plain one-dimensional array. All capabilities are flattened regardless of business domain, scene, or context:

`[query-leave-balance, submit-leave-request, approve-leave-request, query-meeting-room, book-meeting-room, query-reimbursement-standard...]`

Real-world businesses are tree-structured and partitioned: leave-management, meetings, reimbursement, work-orders belong to separate domains requiring only subset-capabilities for given contexts. Under the Skill-pattern, the AI sees the full list of skills in every context, causing severe interference.

### 2. Error-rate Explodes as Capability Count Increases

The Skill-pattern exhibits clear scaling ceilings:
- ¡Ü10 skills: barely usable with manual maintenance
- ~50 skills: semantic overlap, frequent model mis-selection
- ~200 skills: largely dysfunctional; prompt optimization yields no remedy
- 1000+ skills: context window overflow, total breakdown

Even with a dozen skills in Nuwa-AI, mis-invocation and maintenance complexity have already appeared. Traditional Skill-patterns will completely collapse when business expands to thousands of capabilities.

### 3. Natural-language Definitions: Untestable, Unverifiable, Non-regressable

This is the most insidious engineering disaster of Skill-patterns: trigger-conditions, constraint-logic and parameter-requirements are all expressed in verbose natural-language prose.

Triple semantic-loss chain: **Developer¡¯s true intent ¡ú wording bias ¡ú probabilistic large-model interpretation**. Every step introduces distortion, ambiguity and deviation.

Consequences for engineering discipline:
- No unit-testing guarantees: cannot assert the model will interpret logic correctly
- No rule-enforced validation: constraints rely on model self-reflection; omissions and misjudgments occur randomly
- No regression-testing: modifying prompt text offers no way to assess scope-of-impact
- No reproducible failures: model interpretation is stochastic; production defects surface without predictable patterns

> Defining engineering interfaces using prose runs counter to sound engineering and standardization principles.

## VI. CAP Paradigm: The Only Viable Engineering Solution for Ten-thousand-scale Capabilities

The CAP capability-container paradigm fundamentally eliminates Skill-pattern pain-points at architectural-level. It does not depend on model intuition or heavy manual maintenance. Deterministic governance is achieved via three-tier structured mechanisms.

### 1. Tree-shaped Business-domain Grouping to Eliminate Flat-list Chaos

CAP capabilities are not stored as flat lists. They are partitioned in tree-form by business-domain for native isolation:
- leave domain ¡ú create, view, submit, approve
- meeting domain ¡ú query_idle, book, cancel
- expense domain ¡ú query_std, submit_claim
- workitem domain ¡ú list, update_field, submit

Clear capability classification and well-defined boundaries support unbounded business-domain expansion.

### 2. Focus-based Scene Isolation: AI Only Sees a Small Set of Active Capabilities

Core CAP mechanism: **Session Focus**. Upon entering a specific business scene, the session locks onto the corresponding business-domain. The architecture automatically masks all unrelated capabilities.

Whether the total system hosts 10 or 10-000 capabilities, the AI only sees 3-8 scene-relevant anchors per decision-cycle. Mis-selection, mis-invocation and semantic interference are largely eliminated.

### 3. Structured Anchor Contracts for Testable, Governable Operations

CAP discards ambiguous natural-language definitions and adopts formal structured anchor-contracts:
```json
{
  "fnID": "leave.submit",
  "desc": "Submit leave-application",
  "allowParams": ["startDate", "endDate", "reason", "type"],
  "mode": "submit"
}
```

Parameters, capability-types and execution-rules are formally defined\. Configuration-driven validation plus low-level code-hooks provide hard fallback safeguards\.

Probabilistic model self-judgement is removed\. All capability-invocations, validations and returns support unit-testing, automated regression-testing and precise fault-location\.

## VIII\. Core Conclusions \& Industry Corrections

1. **AI-Skill represents a misguided engineering path**: Assigning host-system execution-capabilities to AI couples cognition and execution, resulting in inherently disordered architectures incapable of scaling or sound engineering practice\.

2. **MCP has merits yet firm boundaries**: MCP unified communication protocols between AI and external systems and resolved early-stage industry fragmentation\. Nevertheless, MCP remains merely a transport-layer standard\. It does not solve capability-governance, scene-convergence or large-scale-management problems and cannot serve as a complete Agent architecture\.

3. **Key industry fallacy**: Equating *transport-protocols \(MCP\)* with a full architectural-system; equating *flat tool-lists* with standardized capability-governance\.

4. **Next-generation AI-engineering answer**: MCP / HTTP handles communication; CAP / CC handles governance\. Interoperability is achieved at transport-layer; container-based architecture enforces upper-level governance\.

In the early era of AI development, MCP was needed to unify *how systems communicate*\. As the industry matures, we need CAP to unify *how capabilities are organized*\.

Abandon the outdated AI-Skill mindset and escape the low-level arms-race of adding tools and refining prompts\.
