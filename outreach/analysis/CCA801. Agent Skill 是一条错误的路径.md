# CCA801. Agent Skill 是一条错误的路径
## 一、当下行业的主流误区：把「调度能力」当成「执行技能」

目前整个 Agent 生态，所有人都在聊一件事：给 AI 装配 Skill、给 Agent 堆工具、让大模型拥有更多能力。

行业普遍认知是：大模型 + 更多 Skill = 更强的智能体。

这套看似正确的开发模式，本质是架构认知错位，也是当前所有 Agent 工程混乱、难治理、难复用、无法规模化的根源。

**本文核心立论：**

不存在属于 AI、属于 Agent 的执行技能。所有所谓的 AI Skill，全部都是外部宿主系统的容器能力。AI 本身不具备任何执行能力，仅拥有认知调度能力。

## 二、正本清源：大模型只有「认知能力」，没有「执行能力」

大模型本体，仅具备四类纯认知能力：理解、推理、规划、决策。

我们日常归类为“AI 技能”的动作：读写文件、执行命令、操控电脑、查询业务数据、提交表单、调用接口……没有一项是大模型可以独立完成的，全部依赖浏览器、终端、操作系统、后端服务、第三方系统等外部宿主环境执行。

行业最常见的反驳：Function Calling 就是大模型的能力，能选函数、填参数，就是 AI 的技能。

这是典型的认知混淆：

> 决定“调什么、怎么调”是认知调度，不是业务执行。

如同项目经理可以统筹工人施工、规划工序，但我们不会说“项目经理拥有砌墙、贴砖的施工技能”。**认知调度 ≠ 落地执行**。混淆二者，是 Agent 架构乱象的核心根源。

## 三、正确范式：所有执行能力，都归属于 CC 能力容器

替代 AI-Skill 乱象的唯一合规架构，是 CC 能力容器范式：任何可完成「输入→计算→输出」的宿主环境，都是独立的能力载体，AI 仅做挂载调度，不持有任何执行能力。

常见标准化能力容器：

- 浏览器前端 = Web-CC（页面跳转、表单交互、数据查询）
- 移动端 App = Mobile-CC（语音、摄像、原生交互）
- PC 操作系统 = PC-CC（命令行、文件、窗口、设备操控）
- 后端业务服务 = Biz-CC（业务 CRUD、规则校验、流程审批）
- MCP Server = 设备能力适配传输容器（统一通信层）

所有宿主能力，统一注册为标准化能力锚点，包含唯一标识、语义描述、结构化参数、执行模式、权限约束。

> AI/Agent 的唯一职责：解析用户意图 → 匹配场景焦点 → 调度对应容器锚点 → 交由宿主落地执行。
> AI 是调度中枢，从不生产能力。

## 四、客观看待 MCP：有历史价值，但不是架构方案

当下行业普遍神化 MCP，将其等同于完整 Agent 架构，这是严重的层级误判。我们需要客观、辩证地定义 MCP 的价值与边界。

### 1. MCP 的真实历史价值（不可否定）

MCP 诞生于 2024 年底，彼时整个 AI 行业处于混沌状态：AI 没有统一方式连接外部数据、调用外部工具、对接终端设备。各家私有协议百花齐放，完全没有通用标准。

MCP 的核心贡献，是统一了 AI 与外部系统的通信协议，类比行业基础设施：如同 USB 统一了外设接口，无论鼠标、键盘、U盘都可通用适配。MCP 解决了「AI 如何和外部世界对话」的基础问题，终结了协议碎片化乱象，这是实打实的历史价值。

### 2. MCP 的本质局限：仅为传输层，无架构治理能力

MCP 定位是通信协议层，而非架构范式层，二者有本质区别：

- **MCP**：解决「AI 与外部系统怎么通信、工具怎么传输、结果怎么回传」，是工具调用的传输标准。
- **CAP/CC 范式**：解决「能力归属于谁、如何分组、如何按场景收敛、如何规模化治理」，是完整的能力组织架构。

最关键的问题：MCP 没有跳出传统 Skill 思维惯性。MCP 暴露的 tools 列表，依旧是一维扁平列表、依赖大段自然语言描述、靠大模型概率性理解。它只是给传统 Skill 套了一层标准协议外壳，完全没有解决 Skill 模式的核心痛点：无层级、无场景、不可测、不可校验、无法规模化。

### 3. 正确层级关系：CAP 架构层 > MCP 传输层

二者不是对立关系，是上下层互补关系：

MCP 是 CAP 架构的底层传输适配器，CAP 可以直接兼容 MCP 协议，将 MCP 的 tools 自动转换为 CC 标准化锚点。

完整分层架构：

```
┌────────────────────────────────────────────┐
│  CAP 架构层（能力治理核心）                  │
│  能力归属容器化、场景焦点收敛                │
│  结构化锚点契约、可测可校验                   │
│  事务、权限、生命周期统一管控                 │
└──────────────────┬─────────────────────────┘
                   │ 兼容对接
┌──────────────────▼─────────────────────────┐
│  MCP / Function Calling / HTTP（传输层）    │
│    统一 AI 与外部系统通信协议                │
│    标准化工具调用与结果回传                   │
└────────────────────────────────────────────┘
```

> 总结 MCP 定位：MCP 解决了“怎么通”，CAP 解决了“怎么管”。通信标准已经成熟，行业当下真正缺失的，是能力组织与规模化治理架构。

## 五、一线工程实证：Skill 模式已现天花板（女娲AI现状）

我们当前项目「女娲AI」已经直观暴露传统 Skill 模式的致命缺陷，且这些问题无法靠优化文案、人工管理解决，是范式天生短板。

### 1. 扁平列表结构，业务越大越混乱

Skill 是纯一维数组结构，所有能力被强行拍平，无视业务域、场景、上下文：

`[查请假余额, 提交请假, 审批请假, 查会议室, 预定会议室, 查报销标准...]`

真实业务是树状隔离的：请假、会议、报销、工单分属不同业务域，不同场景仅需对应能力。但 Skill 模式下，无论用户处于什么上下文，AI 都会看到全量技能列表，干扰极强。

### 2. 能力数量上涨，错误率指数爆炸

Skill 模式有明确的能力上限：

- 10 个以内：勉强人工维护可用
- 50 个：语义重叠、模型频繁选错
- 200 个：基本不可用，文案优化也无解
- 1000+：上下文溢出、彻底崩盘

目前项目仅十多个 Skill 已出现混乱、误调用、难维护问题，未来业务扩张至数千级能力时，传统 Skill 模式会完全失效。

### 3. 自然语言定义：不可测、不可校验、不可回归

这是 Skill 模式最隐蔽、最致命的工程灾难：所有技能的触发条件、约束逻辑、参数要求，全部依赖大段自然语言描述。

形成三重语义损耗：**开发者真实意图 → 文字表达偏差 → 大模型概率性理解**，每一层都会失真、歧义、跑偏。

直接导致工程化完全失控：

- 无法单元测试：不能断言模型必然理解正确
- 无法规则校验：约束依赖模型自省，随时漏判、错判
- 无法回归验证：修改文案，无法评估影响范围
- 无法问题复现：模型理解具有随机性，生产问题无规律爆发

> 用散文文案定义工程接口，本身就是反工程、反标准化的设计。

## 六、CAP 范式：唯一支撑万级能力的工程解决方案

CAP 能力容器范式，从架构层面彻底根治 Skill 所有痛点，不靠模型悟性、不靠人工维护，靠三层结构化机制实现确定性治理。

### 1. 业务域树形分组，告别扁平混乱

CAP 能力并非一维列表，而是按业务域树形拆分，天然隔离：

- leave 请假域 → create、view、submit、approve
- meeting 会议域 → query_idle、book、cancel
- expense 报销域 → query_std、submit_claim
- workitem 工单域 → list、update_field、submit

能力分类清晰、边界明确，支持无限业务扩展。

### 2. Focus 焦点隔离，AI 永远只看少量有效能力

CAP 核心机制：**会话焦点（Focus）**。用户进入特定业务场景，会话自动锁定对应业务域，架构自动屏蔽全量无关能力。

无论系统总共有 10 个还是 10000 个能力，AI 单次决策仅可见 3-8 个当前场景锚点，彻底杜绝选错、误调、语义干扰问题。

### 3. 结构化锚点契约，实现可测可管控

CAP 摒弃模糊的自然语言定义，采用标准化结构化锚点契约：
```json
{
  "fnID": "leave.submit",
  "desc": "提交请假申请",
  "allowParams": ["startDate", "endDate", "reason", "type"],
  "mode": "submit"
}
```

参数、能力类型、执行规则全部结构化定义，搭配配置化校验 \+ 底层代码钩子硬兜底。

彻底摆脱模型概率性自省，所有能力调用、校验、返回均可单元测试、自动化回归、精准定位问题。

## 七、终极对比：Skill 模式 VS CAP 容器模式

|对比维度|传统 Skill/MCP-Tools 模式|CAP 能力容器范式|
|---|---|---|
|能力结构|一维扁平列表，无层级、无场景|业务域树形结构，天然隔离解耦|
|AI 可见范围|全量技能灌入 Prompt，上下文爆炸|Focus 焦点收敛，仅展示当前场景能力|
|能力定义方式|长文本自然语言，模糊、歧义、不可控|结构化契约，参数、规则、类型明确|
|错误根源|模型幻觉、理解偏差、文案歧义|架构约束兜底，消除概率性错误|
|工程特性|不可测、不可校验、不可回归|全链路可单测、可自动化、可运维|
|规模化能力|10\+ 混乱、50\+ 失效、无法规模化|支持万级能力无限扩展，稳定可控|
|架构层级|仅传输层，无治理能力|架构层，负责能力归属、组织、调度、治理|

## 八、核心结论与行业纠偏

1. **AI Skill 是错误的工程路径**：将宿主执行能力归属于 AI，认知与执行耦合，架构天生混乱，无法规模化、无法工程化。

2. **MCP 有功但有界**：MCP 统一了 AI 与外部系统的通信协议，解决了行业早期碎片化问题，具备真实历史价值。但 MCP 只是传输层标准，不解决能力治理、场景收敛、规模化管理问题，不能作为完整 Agent 架构。

3. **行业核心误区**：将 “传输协议（MCP）” 等同于 “架构体系”，将 “扁平工具列表” 等同于 “标准化能力治理”。

4. **下一代 AI 工程标准答案**：MCP/HTTP 负责通信，CAP/CC 负责治理；底层靠协议互通，上层靠容器架构管控。

## 九、行动指南（落地准则）

所有 AI Agent 项目，应当停止堆砌、优化、扩充 Skill 列表。

**落地判断标准：**

> 任何一项可执行能力，优先判定归属：属于宿主系统，而非 AI。
> 
> 

将所有能力从 Agent 中剥离，按业务域构建 CC 能力容器，标准化注册锚点，通过 Focus 机制做场景收敛，AI 仅负责认知调度。

> AI 永不持有技能，只挂载、调度、分发系统能力。
> 
> 

## 十、结语

AI 行业早期，我们需要 MCP 统一 “对话方式”；行业成熟后，我们需要 CAP 统一 “能力组织方式”。

抛弃过时的 AI-Skill 思维，跳出 “堆工具、堆文案” 的低级内卷，用容器化、结构化、场景化的 CAP 架构，解决行业真正的核心难题：万级能力的标准化治理与确定性调度。
