# 102.2.1 元语

**定义**：元语是角色之间交互的语义契约。角色调用元语，与其他角色完成具备特定语义的通讯，无需感知底层实现细节。

**元语层与底层实现相互独立**：元语仅定义角色交互的语义范式、会话时序、应答契约；报文编解码、网络传输、消息投递、可靠性保障等属于底层协议职责，不在元语契约覆盖范围。底层仅负责报文投递，不解析元语业务语义、不执行会话规则、不做应答时序校验。角色开发者只调用元语方法，只关心语义契约，完全不用感知底层是何种传输通道、何种序列化格式。元语契约稳定不变，底层传输可独立替换、升级，互不影响。

**元语分为三大交互类型**：
1. 发送不管（事件型：emit）
2. 发送等回应（同步请求：call/return）
3. 发送不阻塞，注册 on 回调等待 1~N 次应答（异步流式：post/notify/return）

**说明**：
- call /post：发起类元语（对外发起交互请求）
- return /notify：应答类元语（用来回复 call /post）

## 1. 发送不管（事件型：emit）

角色发出消息之后，不阻塞、不等待对方任何业务应答。仅做单向信息推送。
对应元语：emit
**emit**：广播类事件，一对多分发，契约层面不要求任何回执，发送方不等待接收方应答。底层传输层的消息 ack 属于技术实现细节，不在本语义契约定义范围内。

**运行机制**：接收角色通过统一入口 on (事件报文) 捕获 emit 事件报文；on 识别报文元语标识为 emit，仅消费事件，不输出应答报文。
emit 在元语契约层面不定义接收回执，无 return、无 notify。post 的框架回执属于元语契约层定义的接收确认，emit 不包含该回执。
emit 事件消费失败由消费方自行处理，发送方不感知、不负责。

**报文规则**：emit 请求携带 payload；不存在业务应答报文。

## 2. 发送等回应（同步请求：call/return）

角色发出请求，调用阻塞，原地等待对方返回一次 return 应答，收到 return 后本次交互结束。

对应发起元语：call；应答元语：return

**call**：同步请求范式，调用方阻塞等待，用于元数据查询、容器枚举、能力信息读取。

**运行机制**：接收角色通过统一入口 on (事件报文) 捕获 call 请求报文；on 识别报文元语标识为 call，执行业务逻辑，调用 return 元语返回业务应答报文。

**报文规则**：call 请求携带 payload；return 应答报文承载业务数据。header 承载框架级状态码；业务层可在 payload 内部自定义业务返回码。

**契约约束**：
call 会话中 return 仅允许 1 条。目标角色重复发送 return 视为协议违规。发起角色收到 return 后会话闭合，后续收到同一会话的 return 直接丢弃。同一会话内，发起方仅处理第一条 return。

## 3. 发送不阻塞，注册 on 回调等待 1~N 次应答（异步流式：post/notify/return）

角色发出请求，调用立刻返回不阻塞；预先注册 on 回调，后续可接收多条应答消息，直到收到 return 标记会话终结。

对应发起元语：post；应答元语：notify（0…N 条） + return（1 条，收尾）

**post**：异步定向投递范式，定向发给单一目标角色，对方必须返回接收回执（仅代表报文已接收入队，回执不携带业务结果；业务结果由后续 notify、return 回传），用于对话链路各类长任务、流式事件投递。

**运行机制**：接收角色通过统一入口 on (事件报文) 捕获 post 请求报文；on 识别报文元语标识为 post，返回接收回执；后台执行业务，可多次调用 notify 推送中间分片、进度、中间事件；任务全部完成后调用 return，作为本次 post 任务的终结应答。

**契约约束**：
return 在同一 post 会话中有且仅有 1 条。收到 return 后发起方标记该 correlation_id 对应的会话闭合，后续再收到同一 correlation_id 的 notify/return 直接丢弃。目标角色重复发送 return 视为协议违规。
notify 仅允许在 return 之前推送。一旦发送 return，目标角色不得再向该 correlation_id 推送 notify。

**报文规则**：post 请求携带 payload；回执仅携带框架状态，无业务载荷；notify、return 携带业务载荷。

## 内部链路元语（不对外暴露，不属于上面三类交互类型）

**on**：角色统一报文捕获入口。所有入站报文（call /post/emit /return/notify /forward）均经由 on 捕获。on 不属于对外可调用元语；收到报文后，读取报文元语标识，驱动后续应答行为。

**forward**：链路透传转发元语，仅限系统内部转发，不生成新业务请求与应答；完整继承原始报文的元语契约。forward 不分配独立 msg_id，直接透传原始报文 msg_id 与 correlation_id。目标角色 on 收到 forward 报文，按原始 meta.primitive 处理；应答报文（return/notify）直接回传给原始发起方，不再经过 forward 中转节点。

## 交互流程

call 属于发送等回应模型。发起角色调用 call，向外送出请求报文；报文送达目标角色，进入目标角色唯一统一入口 on (事件报文)；on 捕获报文，读取报文内部元语标记，识别这是 call 类型报文；目标角色执行业务逻辑，组装应答数据，调用 return 元语发送应答报文。发起角色的 call 调用阻塞，直到收到 return 报文，调用解除阻塞，拿到结果。

post 属于发送不阻塞，注册 on 回调等待 1~N 次应答模型。发起角色调用 post，发出请求后调用直接返回，不阻塞；目标角色返回框架接收回执，后台持续执行任务。任务执行期间，目标角色可多次发送 notify，向发起角色推送中间数据；任务全部结束，目标角色发送 return。发起角色的 on 持续接收 notify，收到 return 后标记本次 post 任务会话闭合，不再处理该任务的后续消息。

> **关键点**：on 是接收报文的入口函数；
>  入站报文是 call：on 执行业务，调用 return 元语发送应答报文。return 就是 call 同步等待的返回数据。
>  入站报文是 post：on 立刻返回框架回执，后台业务异步执行，可输出多条 notify，最终输出一条 return 收尾。

## 标识生成规则

- msg_id：由发起方框架在创建请求报文时自动生成，全局唯一。
- correlation_id：由发起方在请求报文中设置，值为目标角色应答时回填的引用标识；请求报文中 correlation_id 可为空（首次发起）或指向父请求（链式调用）。

msg_id 用来标记单条消息实例；correlation_id 用来把请求、应答配对，保证链路唯一绑定。

return.correlation_id 回填为原始 call.msg_id 或原始 post.msg_id；
notify.correlation_id 回填为原始 post.msg_id。

## 元语对照表

| 交互模型 | 发起元语 | 应答元语 | 阻塞特性 |
| --- | --- | --- | --- |
| 发送不管（事件型） | emit | 无 | 非阻塞 |
| 发送等回应（同步请求） | call | return | 阻塞，等待单条 return |
| 注册回调等待多应答（异步流式） | post | notify (0…N 条)+return (1 条收尾) | 非阻塞 |

## 协议违规约定

1. 收到未知元语类型：直接丢弃报文，不生成应答；
2. 会话已闭合后收到同 correlation_id 报文：直接丢弃；
3. 违反时序约束（return 后继续发 notify、重复 return）：判定协议违规。
