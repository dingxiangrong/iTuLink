## 102.3.1.2 UPP 初始化流程

## 前置说明

本小节所有组件（UPP、CC、SV、SE）均派生自 Endpoint 基类，继承全套元语方法（call /post/notify /return/emit /forward/on）。其中 UPP、CC、SE 各自携带独立 crid 唯一通信标识；**SV 为壳式组件，不占独立 crid 坑位，其注册所用 crid 即 CDT 的 crid**。

### 1. 术语与角色定义

- **UPP** —— 宿主应用，自治域主体。平台提供 BaseUPP 基础类；业务应用继承 BaseUPP 扩展为具体宿主。UPP 是 Endpoint 的派生实现。
- **BaseUPP** —— 平台基础类，内部私有托管本自治域唯一 EventBus 实例，对外暴露 on /emit 订阅发布接口。业务应用无权、无需手动创建总线。BaseUPP 继承 Endpoint。
- **EventBus** —— 隶属于单个 UPP 自治域的消息总线，维护 "CRID → 消息队列" 映射，统一完成队列注册、消息寻址与入队投递。总线依据报文 meta 内 src_crid /dest_crid 完成路由。
- **CC** —— 能力容器 / 胶水中间件，由 UPP 实例化，内置代理封装粘合各类异构底层能力。CC 继承 Endpoint。
- **SV** —— 基础中间件，负责会话管理、事件分发、CC 路由寻址。**SV 是壳式组件，本身无独立身份、不占 crid 坑位，注册所用 crid 即 CDT 的 crid，本地域内寻址 CDT 即寻址 SV**。SV 继承 Endpoint。
- **SE** —— 补充组件，负责外延能力（如对外接口、扩展服务）。SE 继承 Endpoint。
- **CRID** —— Endpoint 实例唯一通信标识。每个承载身份的 Endpoint 实例分配独立 CRID，并与一条专属消息队列绑定，作为 meta 中 src_crid、dest_crid 取值来源。SV 不额外占用独立 CRID。

### 2. 总线模型

#### 2.1 总线归属

- 一个 UPP 自治域对应一条 EventBus；
- EventBus 由 BaseUPP 构造时自动实例化，业务代码不可见、不可手动创建；
- 单进程内可存在多个 UPP 自治域，各自持有一条独立总线，域间天然隔离；
- UPP 销毁时，其托管的 EventBus 连同全部 Endpoint 实例队列一并回收。

#### 2.2 类比说明

EventBus 之于 UPP 自治域，类比 Windows 系统消息池之于进程：系统（UPP / BaseUPP）建立自治域消息队列池，各通信端点（CC / SV / SE / UPP）在池中各自占用一条独立消息队列。业务开发者只编写端点消息处理逻辑，不参与消息池的创建与管理。

#### 2.3 总线结构

```
UPP（自治域根宿主，BaseUPP，Endpoint 派生）
 └── EventBus（自治域私有总线，BaseUPP 内部托管）
      ├── crid_upp   → UPP 队列
      ├── crid_cc1   → CC-1 队列
      ├── crid_cc2   → CC-2 队列
      ├── crid_cdt   → SV 队列（即 SV 注册所用 crid，为 CDT 的 crid）
      └── crid_se    → SE 队列
```

### 3. 初始化时序（严格顺序，不可颠倒）

1. **UPP 实例化**：业务应用创建 UPP 实例，执行父类构造。BaseUPP（Endpoint 子类）构造内部自动实例化 EventBus，生成 UPP 自身 CRID，并在总线注册 UPP 专属队列。业务代码不感知总线创建过程。
2. **CC 实例创建与就绪**：UPP 按需实例化一个或多个 CC 能力容器。每个 CC（Endpoint 派生）在实例化时，构造内部自动生成自身 CRID，并向 UPP 托管的 EventBus 注册专属队列；随后 CC 启动内部代理，加载、绑定自身对应的底层能力，完成内部能力粘合适配。全部 CC 实例创建、注册、就绪。
3. **SV 实例创建**：UPP 实例化 SV。SV（Endpoint 派生）为壳式组件，构造时注册所用 CRID 即 CDT 的 CRID，向 EventBus 注册专属队列，对外以 CDT 的 CRID 作为本地域寻址地址。
4. **SE 实例创建**：UPP 按需实例化 SE。SE（Endpoint 派生）构造内部自动生成自身 CRID，向 EventBus 注册专属队列。
5. **UPP 注册元语处理器**：业务应用在 UPP 内实现元语事件处理器：
   - upp-meta-get：收到该元语请求时，返回 UPP 自身元数据；
   - upp-cc-enum：收到该元语请求时，枚举返回当前已创建就绪的全部 CC 实例清单。
6. **SV 内部初始化**：SV 向 EventBus 发起元语调用：
   - call (destUppEp, "upp-meta-get", payload, ctrlMap)：读取 UPP 主体元信息；
   - call (destUppEp, "upp-cc-enum", payload, ctrlMap)：获取全部 CC 清单，构建内部 CRID 路由寻址表。
7. **进入运行态**：初始化完成。业务应用通过 emit 推送会话生命周期事件（session-in /session-out）；EventBus 读取报文 meta 中 dest_crid 寻址入队；SV 从自身队列消费事件，依据路由表将业务请求转发至对应 CC。

### 4. 组件自动注册规则

所有附属组件（CC / SV / SE）在构造阶段自动完成总线注册：

- 组件被 UPP 实例化时，组件自身构造函数内完成队列注册（SV 注册所用 CRID 即 CDT 的 CRID）；
- 业务代码只需创建组件实例，无需编写任何注册逻辑；
- 业务应用仅通过 on 注册事件处理器、通过 emit 发送事件，不触碰 EventBus 底层队列管理。

### 5. 关键约束

1. 时序不可颠倒：CC 必须先全部创建就绪并注册总线，再实例化 SV。顺序颠倒会导致 SV 调用 upp-cc-enum 时返回空 CC 列表，路由表无法完整构建。
2. CC 仅由 UPP 实例化：SV 不负责创建或销毁 CC。upp-cc-enum 仅为元语查询，读取 UPP 现存 CC 清单。
3. 总线创建权归平台：EventBus 是 BaseUPP 的私有资产，业务开发者不可手动创建总线对象。
4. 通信统一走总线：所有元语请求、应答、生命周期事件，一律经由 UPP 托管的 EventBus，依靠报文 meta 的 src_crid /dest_crid 完成投递，不采用函数回调直连。
5. 所有通信单元均为 Endpoint 派生，元语调用时，源端点自动填充 src_crid，目标端点对象提取 dest_crid，业务层不直接操作 CRID 字符串。SV 作为壳，本地域寻址 CDT 时 dest_crid 填 CDT 的 crid（即 SV 注册所用 crid）。

### 6. 分层边界

- **平台层** —— 职责：BaseUPP 托管 EventBus、封装 CRID 注册、消息投递、请求应答配对、队列管理、Endpoint 基类元语实现。不可触碰：无。
- **业务应用层** —— 职责：继承 BaseUPP，实现 on 元语处理器、调用 emit 发事件、实例化 CC/SV/SE。不可触碰：总线对象、队列底层、CRID 手动赋值。
